# Delta — แผนงานและชุดคำสั่งพัฒนา

ไฟล์นี้คือแผนงานหลักของโปรเจกต์ ใช้แทนแผน 16 phase เดิมทั้งหมด

**วิธีใช้:** สั่งงานทีละ prompt (`ทำ P1 ตาม docs/PLAN.md`) หนึ่ง prompt ต่อหนึ่งรอบงาน
ห้ามรวมหลายด่านในรอบเดียว · ปิดท้ายทุกด่านด้วย **P8** เสมอ

## 1. กติกาสามข้อที่ทุกฟีเจอร์ต้องผ่าน

**1) แผนต้องถูกสร้างให้ ไม่ใช่ให้ผู้ใช้นั่งกรอก**
ผู้ใช้ตอบ 3 อย่างเท่านั้น — สอบสนามไหน / สอบวันไหน / ว่างวันละกี่นาที
ที่เหลือระบบสร้างเองจากบทที่ยังไม่ผ่าน ลำดับพื้นฐาน และ `estimatedMinutes` จริงที่มีอยู่แล้ว
การแก้ด้วยมือมีได้ แต่เป็นทางเลือก ไม่ใช่ทางหลัก

**2) ทุกกราฟวาดจากเหตุการณ์ที่บันทึกไว้ ห้ามวาดจากตัวเลขที่เก็บไว้**
เก็บ "ตอบข้อไหน เมื่อไร ถูกหรือผิด ใช้เวลากี่วินาที" เป็นแถวในตาราง แล้วคำนวณตอนแสดงผล
ห้ามเก็บ `accuracy = 72` ลงฐานข้อมูล เพราะวันที่อยากได้กราฟย้อนหลัง ข้อมูลนั้นจะไม่มี
**นี่คือการตัดสินใจทางเทคนิคที่สำคัญที่สุดในแผนนี้ และต้องถูกตั้งแต่ด่านแรก ๆ**

**3) ข้อมูลรับเข้ามหาวิทยาลัยต้องมีที่มาและวันที่ตรวจสอบติดทุกแถว**
ทุกรายการต้องมีลิงก์แหล่งทางการ วันที่ตรวจล่าสุด และสถานะ 3 แบบ:
ประกาศแล้ว / คาดการณ์จากปีก่อน / **รอประกาศ**
ห้ามเดาวันที่เด็ดขาด แม้จะ "น่าจะประมาณนี้"

### ขอบเขตของ "ทุกรอบอย่างละเอียด"
- ปฏิทิน**ระดับประเทศ** (4 รอบของ ทปอ.) ≈ 40–60 แถวต่อปี แหล่งเดียว → ทำได้จริง ทำก่อน
- ปฏิทิน**รายมหาวิทยาลัยทุกแห่ง** = หลายร้อยแหล่งที่ประกาศไม่พร้อมกันทั้งปี → เป็นงานประจำ ไม่ใช่ฟีเจอร์
- เริ่มที่ 5–10 แห่งที่ตามไหว ที่เหลือแสดง "ยังไม่มีข้อมูล" พร้อมลิงก์ไปเว็บรับสมัครของที่นั่น

### ยังอยู่นอกขอบเขต (ห้ามเพิ่ม)
Portfolio · SOP · ฐานข้อมูลเกณฑ์คะแนนรับเข้า · ข่าว TCAS
(ปฏิทิน**วันที่**รับสมัคร กับ**เกณฑ์**รับเข้า เป็นคนละเรื่องกัน)

## 2. โครงสร้างข้อมูล

ตารางผู้ใช้อยู่บน Supabase เปิด RLS ทุกตาราง
ตารางสอบและรายชื่อมหาวิทยาลัย **ไม่ใช่ข้อมูลผู้ใช้** → เก็บเป็นไฟล์ข้อมูลใน repo เหมือนบทเรียน

| ตาราง | เก็บอะไร | ข้อควรระวัง |
|---|---|---|
| `profiles` | ชั้นปี · สนามสอบที่เล็ง · เขตเวลา · วันที่ยินยอม | เก็บให้น้อยที่สุด ไม่เก็บโรงเรียน/เบอร์โทร |
| `attempts` | ทุกครั้งที่ตอบโจทย์: ข้อไหน ถูกไหม กี่วินาที เมื่อไร | **หัวใจของทุกกราฟ** ไม่มีตารางนี้ = กราฟย้อนหลังสร้างไม่ได้ตลอดไป |
| `study_sessions` | ช่วงเวลาที่เรียนจริง: บทไหน เริ่ม–จบเมื่อไร | ตัดช่วงที่ไม่มีการกระทำเกิน 5 นาทีทิ้ง |
| `lesson_progress` | สถานะรายบท + เวลาเริ่ม/จบ | ต้องรวมข้อมูลของแขกเข้าบัญชีตอนล็อกอินครั้งแรก |
| `exam_results` | ผลข้อสอบจำลอง: คะแนน เวลา จุดอ่อนรายบท | รายละเอียดรายข้ออยู่ใน `attempts` |
| `plans` | สนามสอบ วันสอบ วันเริ่ม นาที/วัน สถานะ | หลายแผนได้ แต่ active ทีละแผน |
| `plan_items` | รายการของแต่ละวัน: ทำอะไร กี่นาที เสร็จหรือยัง | ระบบสร้างให้ ผู้ใช้แก้ได้ |
| `tasks` | งานที่ผู้ใช้พิมพ์เอง (ชนิด · วิชา · กำหนดส่ง) + งานที่ระบบสร้าง (`source`) | พิมพ์งานนอก Delta ได้ทุกวิชา · วิชาเป็นข้อความอิสระ ห้ามทำเป็น enum |
| `exam_schedule` *(ไฟล์ใน repo)* | ปี · กลุ่มสอบ (TGAT/TPAT1-5/A-Level) · รายวิชา · วันเวลาสอบ · สถานะ · แหล่งอ้างอิง · วันที่ตรวจ | ตรวจด้วย zod ตอน build · ไม่ต้องล็อกอินก็ดูได้ · นับถอยหลังคำนวณสดเสมอ |
| `watchlist` | สนามสอบที่ผู้ใช้ติดตาม | ใช้ป้อนวันสำคัญเข้าหน้า /today |
| `universities` *(ไฟล์ใน repo)* | ชื่อมหาวิทยาลัย · ชื่อย่อ/ชื่อเล่นที่คนเรียกจริง · คณะที่พบบ่อย | ใช้เป็นตัวช่วยค้นหาเท่านั้น **ไม่ใช่ฐานข้อมูลหลักสูตรฉบับสมบูรณ์** ห้ามอ้างว่าครบทุกหลักสูตร |
| `target_programs` | คณะ/มหาวิทยาลัยที่ผู้ใช้อยากเข้า + ลำดับความอยาก | พิมพ์เองได้เสมอแม้ไม่มีในไฟล์ค้นหา · ห้ามบังคับให้เลือกจากลิสต์อย่างเดียว |
| `notification_prefs` | ผู้ใช้ยอมให้ส่งอีเมลชนิดไหนบ้าง + โทเคนยกเลิก | **ค่าเริ่มต้นต้องเป็นปิดทุกชนิด** เปิดเองเท่านั้น |
| `notification_log` | ส่งอะไรให้ใคร วันไหนไปแล้วบ้าง | กัน cron ยิงซ้ำด้วย unique constraint ไม่ใช่ด้วยการเช็คในโค้ด |

### กับดักสามอันที่เจอบ่อยที่สุด
- **เขตเวลา** — เก็บ UTC เสมอ คำนวณ/แสดงผลด้วย Asia/Bangkok เสมอ ห้าม `new Date("2026-12-14")` ลอย ๆ
- **ข้อมูลแขกหายตอนล็อกอิน** — ต้องรวมแบบเก็บค่าที่ก้าวหน้ากว่า แล้วแจ้งผู้ใช้ ห้ามเขียนทับเงียบ ๆ
- **RLS ไม่ครบ** — ทุกตารางต้องมีครบ select/insert/update/delete และ update ต้องมีทั้ง `using` และ `with check`

## 4. สเปกย่อ

### Study Planner
- **สร้าง** — ถาม 3 คำถาม → ดึงบทที่ยังไม่ผ่าน เรียงตามลำดับพื้นฐาน ใช้ `estimatedMinutes` จริง กระจายลงวันตามเวลาว่าง
- **รายวัน** — หน้า "วันนี้" แสดงรายการ + เวลารวม + ปุ่มเริ่มที่พาเข้าขั้นที่ค้างไว้
- **ตามไม่ทัน** — เสนอ 3 ทางเลือก: เลื่อนทั้งแผน n วัน / เพิ่มนาทีต่อวัน / ตัดบทที่ไม่ออกในสนามสอบนี้ แล้วบอกตรง ๆ ว่า "ตามหลังอยู่ 2 วัน"
- **ห้าม** — ปฏิทินเปล่าให้สร้างกิจกรรมอะไรก็ได้ · แถบเลื่อนลากเปอร์เซ็นต์เอง

### To-do
- สองชนิดในรายการเดียว แยกด้วยป้าย: งานที่ระบบสร้าง (ติ๊กแล้วความก้าวหน้าขยับจริง) กับงานที่ผู้ใช้พิมพ์เอง (อิสระ)
- งานที่พิมพ์เองครอบคลุมทุกวิชา ไม่ใช่แค่คณิต — มีชนิดงาน (งานทั่วไป/การบ้าน/สอบ) และชื่อวิชาแบบพิมพ์เอง
- ฟอร์มไม่เกิน 5 ช่อง สร้างงานจบใน 10 วินาที
- แยกให้ชัดระหว่าง "ทำงานเสร็จ" กับ "เก่งขึ้น"

### กราฟ 6 แบบ
1. ความแม่นยำรายวัน 30 วัน (เส้น) ← `attempts`
2. นาทีเรียนจริงต่อวัน 14 วัน (แท่ง + เส้นเป้า) ← `study_sessions` + `plans`
3. บทที่ผ่านสะสม (เส้นขั้นบันได) ← `lesson_progress`
4. ความแม่นรายหัวข้อ เรียงจากอ่อนสุด (แท่งแนวนอน) ← `attempts`
5. คะแนน mock ตามเวลา (เส้น + จุด) ← `exam_results`
6. ความสม่ำเสมอ 12 สัปดาห์ (heatmap) ← `study_sessions`

**กติกา:** ข้อมูลไม่พอ → บอกว่ายังไม่พอและต้องทำอะไรอีกเท่าไร ห้ามลากเส้นศูนย์ · มีหน่วยและช่วงวันที่ทุกอัน · อ่านออกทั้งสองธีม · วาดด้วย SVG บนแกนที่มีอยู่แล้ว ไม่ลงไลบรารีใหม่

### ตารางสอบ TGAT/TPAT/A-Level
- ทุกสนามสอบของรอบปัจจุบัน · กรองตามกลุ่มสอบและรายวิชาได้ · เข้าดูได้โดยไม่ต้องล็อกอิน
- **บนสุดของหน้าคือป้ายใหญ่ของสนามสอบที่ใกล้ที่สุดเพียงอันเดียว** นับถอยหลังเป็นวัน/ชม./นาที/วินาที
- การ์ดแต่ละใบ: ชื่อสนามสอบ · วันเวลาสอบ · สถานะ · แหล่งอ้างอิง · "ตรวจสอบล่าสุดเมื่อ …"
- `verifiedAt` เก่ากว่า 60 วัน → ขึ้นป้าย "ข้อมูลอาจไม่อัปเดต" อัตโนมัติ
- กดติดตาม → วันสำคัญไปโผล่ในหน้า /today และนาฬิกานับถอยหลัง
- ทุกหน้าต้องมี: "ข้อมูลนี้รวบรวมเพื่อความสะดวก ยึดประกาศจากแหล่งทางการเป็นหลักเสมอ" + ลิงก์ mytcas

### คณะ/มหาวิทยาลัยเป้าหมาย
- พิมพ์แล้วขึ้นรายการใกล้เคียงทันที · เลือกจากรายการหรือใช้ข้อความที่พิมพ์เองก็ได้
- เก็บได้หลายอันดับ เรียงลำดับความอยากได้ · แก้/ลบได้ตลอด
- **ไม่ใช่ระบบทำนายโอกาสสอบติด** ห้ามคำนวณเปอร์เซ็นต์ว่าจะติดหรือไม่ติดจากข้อมูลที่มี

### P2.1 — ปิดรูรั่วที่ค้างจาก P2: ผลฝึกและผลสอบยังไม่ขึ้นคลาวด์

ซึ่งดีกว่าโกหก แต่เป็นการอธิบายความไม่สอดคล้อง แทนที่จะแก้มัน

```
ส่งมอบ: ไฟล์ที่แก้ + SQL ที่ต้องรันถ้ามี + ผลการทดสอบสองข้อในข้อ 5

```

```
ส่งมอบ: ไฟล์ที่แก้และเพิ่ม + ภาพหน้าจอจุดที่ยังไม่มีข้อมูลและจุดที่มีข้อมูลแล้ว
```

### P9 — ปรับภาษาภาพ: จริงจังตอนเรียน อบอุ่นตอนไม่ได้เรียน (ทำเมื่อไรก็ได้ ไม่ผูกกับด่านอื่น)

```
10. **ระบบปุ่มเดียวทั้งเว็บ** — ตอนนี้ปุ่มแต่ละหน้าหน้าตาไม่เหมือนกัน หลายอันเป็นแค่กรอบเส้นบาง
    จนดูไม่ออกว่ากดได้ ทำคอมโพเนนต์ `Button` ตัวเดียวแล้วไล่เปลี่ยนทุกหน้าให้ใช้ตัวนี้
    (ห้ามเขียน class ปุ่มซ้ำในแต่ละหน้าอีก) สามระดับ ไม่มีระดับที่สี่:
    - **primary** — พื้นสี accent ทึบ ตัวอักษรตัดกับพื้นชัด เงาอ่อน ๆ หนึ่งชั้น
      หนึ่งหน้าจอมีได้ **ปุ่มเดียว** คือสิ่งที่อยากให้ผู้ใช้ทำที่สุดตรงนั้น
    - **secondary** — พื้นสี accent จาง (tint) ตัวอักษรสี accent เข้ม ไม่มีเงา
    - **ghost** — ไม่มีพื้น มีแค่ตัวอักษร ใช้กับงานรอง เช่น ยกเลิก/ปิด
    กติกาที่ใช้กับทั้งสามระดับ:
    - สูงอย่างน้อย 44px และกว้างอย่างน้อย 44px (มาตรฐานนิ้วโป้ง) แม้ปุ่มไอคอนล้วน
    - มุมมนเท่ากันทุกปุ่ม · ตัวอักษรน้ำหนัก 500-600 ไม่ใช่ตัวหนาโป๊ก
    - hover / active / focus-visible / disabled ต้องต่างกันเห็นชัดครบทุกสถานะ
      active ให้ยุบลงเล็กน้อย (scale ~0.97) ไม่ใช่แค่เปลี่ยนสี
    - focus-visible ต้องมีวงแหวนที่มองเห็นได้จริงทั้งสองธีม (คนใช้คีย์บอร์ดต้องรู้ว่าอยู่ตรงไหน)
    - ปุ่มที่กำลังทำงานอยู่ให้แสดงสถานะกำลังโหลดในตัวปุ่มเอง แล้วกดซ้ำไม่ได้
    - ห้ามใช้ <div onClick> เป็นปุ่มเด็ดขาด ต้องเป็น <button> หรือ <a> จริง

11. **แนวทางภาพรวม: friendly · clean · premium** — ตอนนี้หน้าตายังออกแนว HUD เกม
    เป้าหมายคือความรู้สึกแบบเครื่องมือที่ประณีต ใช้แล้วสบายตา ไม่ใช่หน้าจอคอนโซล
    แปลเป็นของที่จับต้องได้ ไม่ใช่คำอธิบายลอย ๆ:
    - **ที่ว่างคือของหลัก** เพิ่ม padding ในการ์ดและระยะห่างระหว่างบล็อกให้มากกว่าที่คิด
      หน้าหนึ่งควรมีของน้อยลงแต่แต่ละอันหายใจได้ ไม่ใช่อัดให้เต็มจอ
    - **ขอบมน** ใช้สองค่าพอ: การ์ด/แผง 16-20px, ปุ่ม/ช่องกรอก/ป้าย 10-12px
      อย่าใช้ค่าเดียวเท่ากันหมดทั้งเว็บ เพราะทุกอย่างจะแบนเท่ากันจนไม่มีลำดับ
    - **ใช้เงากับพื้นต่างระดับแทนเส้นขอบ** ตอนนี้ทุกอย่างเป็นกล่องมีกรอบ ทำให้รก
      เลือกเน้นเฉพาะของที่ต้องเด่นจริง ไม่ใช่ตีกรอบให้ทุกบล็อกเท่ากัน
    - **ฟอนต์** เลิกใช้ mono เป็นฟอนต์ป้าย (ข้อ 4) แล้วเลือกฟอนต์ไทยที่อ่านสบาย
      น้ำหนักครบ 400/500/600/700 เช่น LINE Seed Sans TH หรือ Noto Sans Thai
      ตั้งสเกลขนาดตัวอักษรไว้ชุดเดียวแล้วใช้ตามนั้นทั้งเว็บ ห้ามตั้งขนาดมั่ว ๆ รายจุด
      ตัวเลขทุกที่ที่เรียงเป็นคอลัมน์หรือเดินนับถอยหลังใช้ tabular-nums
    - **สี** พื้นหลังเป็นสีกลางที่เอียงเข้าหาสี accent นิดหนึ่ง ไม่ใช่เทากลางเป๊ะ
      accent มีสีเดียว · สีบอกสถานะ (สำเร็จ/เตือน/ผิดพลาด) แยกจาก accent ไม่นับเป็นสีที่สอง
    - **ท่วงท่า** เปลี่ยนสถานะที่ 150-250ms ease-out เท่านั้น ไม่มีอนิเมชันวิ่งเข้าหน้าจอ
      และต้องเคารพ prefers-reduced-motion
    - ทำใน globals.css เป็น token ให้หมด แล้วให้ component ดึงจาก token
      ห้าม hardcode ค่าสีหรือระยะในไฟล์ component
    ```

```
   - เคารพ prefers-reduced-motion เหมือนกับที่ทำไว้ใน P7

ส่งมอบ: ไฟล์ที่แก้และเพิ่ม พร้อมอธิบายไฟล์ละบรรทัด และวิธีทดสอบอัปโหลด/ลบรูปด้วยมือ
```

### P11 — ด่าน I: คณะ/มหาวิทยาลัยที่อยากเข้า (ทำหลัง P1)

รู้ว่าเล็งคณะไหนอยู่ ทำให้เว็บพูดเรื่องที่ตรงกับผู้ใช้ได้ เช่น เตือนเฉพาะวิชาที่คณะนั้นใช้
แต่ต้องระวังไม่ให้กลายเป็นการเก็บข้อมูลเกินจำเป็น และไม่ใช่เครื่องทำนายว่าจะติดหรือไม่ติด

```
อ่าน CLAUDE.md ก่อนเริ่ม

1. ไฟล์ข้อมูลช่วยค้นหา src/content/universities.ts (ไม่ใช่ตารางฐานข้อมูล)
   - แต่ละมหาวิทยาลัย: id, ชื่อเต็มทางการ, aliases[] (ชื่อที่คนเรียกจริง เช่น
     "จุฬา" "CU" "ม.เกษตร" "มก." "มอ." "มช." "มธ." "TU") — aliases คือหัวใจของการค้นหา
     เพราะไม่มีใครพิมพ์ชื่อเต็มทางการ
   - รายชื่อคณะที่พบบ่อยเก็บเป็นลิสต์กลางลิสต์เดียว (แพทยศาสตร์ วิศวกรรมศาสตร์ ฯลฯ)
     ใช้ร่วมกันทุกมหาวิทยาลัย ไม่ต้องแตกเป็นรายหลักสูตรของแต่ละที่
   - ใส่มหาวิทยาลัยที่คนสมัครเยอะก่อนสัก 30-40 แห่ง ไม่ต้องครบทุกแห่งในประเทศ
   - **คอมเมนต์หัวไฟล์ต้องเขียนชัดว่านี่คือตัวช่วยค้นหา ไม่ใช่ฐานข้อมูลหลักสูตรฉบับสมบูรณ์**
     และหน้าเว็บห้ามเขียนข้อความที่ทำให้เข้าใจว่าครบทุกหลักสูตร

2. ตาราง target_programs (RLS ครบ 4 policy · update มีทั้ง using และ with check)
   - id, user_id, university_id (null ได้ ถ้าผู้ใช้พิมพ์เอง), university_name (text, ไม่ว่าง),
     faculty_name (text, ไม่ว่าง), program_name (null ได้), rank (int, ลำดับความอยาก),
     note (null ได้), created_at
   - เก็บ university_name เป็นข้อความเสมอแม้จะเลือกจากลิสต์ เพราะถ้าวันหน้าแก้ไฟล์ค้นหา
     เป้าหมายที่ผู้ใช้เคยบันทึกต้องไม่เพี้ยนตาม (หลักเดียวกับที่ใช้กับ lesson slug)
   - unique (user_id, rank) ไม่ต้องมี — ให้เรียงใหม่ได้อิสระ อย่าล็อกจนแก้ลำดับไม่ได้

3. ช่องค้นหาแบบพิมพ์แล้วขึ้นตัวเลือก (combobox) — ทำเป็นคอมโพเนนต์ใช้ซ้ำได้
   - พิมพ์แล้วกรองสด ๆ ฝั่ง client จากไฟล์ข้อ 1 (ข้อมูลไม่กี่สิบแถว ไม่ต้องยิง API)
   - จับคู่ทั้งชื่อเต็มและ aliases · ตัดช่องว่างและคำนำหน้า "มหาวิทยาลัย"/"ม." ออกก่อนเทียบ
     เพื่อให้พิมพ์ "เกษตร" แล้วเจอ "มหาวิทยาลัยเกษตรศาสตร์"
   - เรียงผลลัพธ์: ขึ้นต้นตรงกัน > มีคำนั้นอยู่ข้างใน > ตรงกับ alias
   - **ถ้าไม่มีอะไรตรงเลย ต้องมีตัวเลือก "ใช้คำที่พิมพ์ไปเลย: <ที่พิมพ์>" เสมอ** ห้ามบังคับให้เลือกจากลิสต์
     เพราะลิสต์เราไม่ครบ และจะกลายเป็นการบอกผู้ใช้ว่าคณะที่เขาอยากเข้าไม่มีอยู่จริง
   - ใช้ลูกศรขึ้นลง/Enter/Esc ได้ และใส่ role="combobox" + aria-expanded + aria-activedescendant
     ให้ครบ ไม่ใช่แค่ div ที่กดได้
   - ปิดรายการเมื่อคลิกนอกกรอบหรือกด Esc

4. หน้าจัดการเป้าหมาย (อยู่ใน /settings หรือหน้าแยกก็ได้ เลือกอันที่ทำให้ไฟล์น้อยกว่า)
   - เพิ่ม/แก้/ลบ/เรียงลำดับใหม่ได้ · เพิ่มได้ไม่เกิน 10 อันดับ (เกินนั้นไม่มีประโยชน์จริง)
   - ยังไม่เคยใส่เลย → ข้อความชวนใส่แบบเป็นกันเอง + ปุ่ม primary หนึ่งปุ่ม
   - ทุกปุ่มใช้ระบบปุ่มจาก P9 ข้อ 10

5. เอาไปใช้จริงอย่างน้อยหนึ่งที่ ไม่ใช่เก็บไว้เฉย ๆ:
   หน้า /today หรือ /exams แสดงว่า "เป้าหมายอันดับ 1 ของเธอคือ … " พร้อมลิงก์ไปตารางสอบ
   **ห้ามคำนวณหรือแสดงเปอร์เซ็นต์โอกาสสอบติดเด็ดขาด** เราไม่มีข้อมูลคะแนนขั้นต่ำจริง
   และการเดาตัวเลขแบบนั้นทำร้ายคนใช้มากกว่าช่วย

ส่งมอบ: ไฟล์ที่แก้และเพิ่ม + migration + วิธีเพิ่มมหาวิทยาลัยหนึ่งแห่งลงไฟล์ค้นหา
```

### P12 — ด่าน J: อีเมลแจ้งเตือน (ทำหลัง P6.1 และ P11)

อีเมลเป็นช่องทางเดียวที่ไปถึงคนที่ไม่ได้เปิดเว็บ ซึ่งคือคนที่ต้องการการเตือนที่สุดพอดี
แต่อีเมลที่ส่งผิด ส่งซ้ำ หรือส่งทั้งที่ไม่ได้ขอ ทำให้คนเลิกใช้ทันทีและกู้กลับไม่ได้
รอบนี้จึงเข้มเรื่องการยินยอมและการกันส่งซ้ำมากกว่าเรื่องเนื้อหาอีเมล

```
อ่าน CLAUDE.md ก่อนเริ่ม

1. ตาราง notification_prefs (RLS ครบ 4 policy)
   - user_id uuid primary key references auth.users on delete cascade
   - exam_countdown boolean not null default false
   - registration_deadline boolean not null default false
   - weekly_digest boolean not null default false
   - unsubscribe_token uuid not null default gen_random_uuid() unique
   - updated_at timestamptz not null default now()
   **ค่าเริ่มต้นต้องเป็น false ทุกช่อง** ห้ามเปิดให้อัตโนมัติตอนสมัคร
   ไม่มีแถว = ไม่ส่งอะไรเลย (อย่าถือว่าไม่มีแถวแปลว่ายินยอม)

2. ตาราง notification_log — กันส่งซ้ำด้วยฐานข้อมูล ไม่ใช่ด้วยการเช็คในโค้ด
   - user_id, kind (text), ref_id (text), scheduled_for (date), sent_at timestamptz
   - unique (user_id, kind, ref_id, scheduled_for)
   ลำดับต้องเป็น **insert log ก่อน แล้วค่อยส่งอีเมล** ถ้า insert ชน unique = เคยส่งแล้ว ข้ามไป
   ถ้าส่งกลับกัน cron ที่รันซ้ำ (หรือ deploy ซ้ำ) จะยิงอีเมลซ้ำให้ผู้ใช้ทันที

3. ชนิดที่ส่ง (เริ่มแค่นี้พอ อย่าเพิ่งเพิ่มชนิดอื่น)
   - exam_countdown — สนามสอบใน watchlist เหลือ 30 / 7 / 1 วัน
   - registration_deadline — วันปิดรับสมัครเหลือ 7 / 3 / 1 วัน (จากฟิลด์ที่เพิ่มใน P6.1)
   - weekly_digest — สรุปสัปดาห์: เรียนไปกี่นาที ผ่านกี่บท ตามแผนทันไหม (จากข้อมูลจริงเท่านั้น)
     ถ้าสัปดาห์นั้นไม่มีกิจกรรมเลย **ไม่ต้องส่ง** อีเมลที่บอกว่า "คุณทำ 0 อย่าง" ไม่ช่วยใคร

4. ตัวส่ง: Vercel Cron ยิงเข้า route handler วันละครั้ง (เลือกเวลาเช้าตามเวลาไทย)
   - route ต้องเช็ค secret จาก header ก่อนทำอะไรทั้งสิ้น ใครยิงมั่วต้องได้ 401
   - ใช้ service-role key **ฝั่ง server เท่านั้น** ห้ามให้หลุดไปอยู่ในโค้ดที่ส่งไป browser
     และห้ามใส่ค่าจริงลงไฟล์ที่ commit — ใส่ผ่าน environment variable
   - เลือกผู้รับจาก notification_prefs join watchlist เท่านั้น อย่า query ผู้ใช้ทั้งตาราง
   - อีเมลของผู้ใช้เอามาจาก Supabase Auth ไม่ต้องเก็บสำเนาไว้ในตารางเราเอง

5. เนื้ออีเมล
   - ภาษาไทย สั้น อ่านจบใน 10 วินาที บอกวันเวลาจริงและเหลืออีกกี่วัน
   - มีลิงก์กลับเข้าหน้าที่เกี่ยวข้องตรง ๆ (ไม่ใช่หน้าแรก)
   - **ท้ายอีเมลทุกฉบับต้องมีลิงก์ยกเลิกที่กดแล้วเลิกได้จริงโดยไม่ต้องล็อกอิน**
     ใช้ unsubscribe_token · หน้า /unsubscribe ปิดเฉพาะชนิดที่มาจากลิงก์นั้น
     และต้องยืนยันด้วยการกดปุ่มอีกครั้ง (กันลิงก์โดนเปิดเองโดยตัวสแกนอีเมล)
   - ห้ามใส่รูปติดตามการเปิดอ่าน (tracking pixel) และห้ามเก็บว่าใครเปิดอีเมลตอนไหน

6. หน้าตั้งค่าการแจ้งเตือนใน /settings — สวิตช์สามอัน ตรงกับข้อ 3
   เขียนใต้สวิตช์ให้ชัดว่าแต่ละอันจะส่งเมื่อไรและส่งบ่อยแค่ไหน
   ปิดทั้งหมดได้ด้วยการกดครั้งเดียว

ส่งมอบ: ไฟล์ที่แก้และเพิ่ม + migration + วิธีทดสอบยิง cron ด้วยมือในเครื่องตัวเอง
โดยไม่ส่งอีเมลจริง (โหมด dry-run ที่ log ว่าจะส่งหาใครบ้างแทนการส่ง)
```

> อย่าเพิ่งทำ P12 จนกว่า P6.1 จะใส่วันสอบจริงเรียบร้อย
> อีเมลที่เตือนวันสอบผิดวัน แย่กว่าไม่ส่งอีเมลเลยมาก

## 6. เรื่องที่ต้องคอยระวัง

1. **ตารางสอบเป็นงานประจำ ไม่ใช่ฟีเจอร์ที่ทำเสร็จแล้วจบ** — ตรวจกับ mytcas.com เดือนละครั้ง และให้ป้าย "ข้อมูลอาจไม่อัปเดต" ขึ้นเองเมื่อเกิน 60 วัน · TCAS70 ย้ายวันสอบ TGAT/TPAT จากธันวาคมมาเป็นมกราคม เป็นหลักฐานว่ามันเลื่อนจริงและเลื่อนเยอะ
2. **เนื้อหาคณิตศาสตร์จะหยุดโตระหว่างทำสี่ด่านนี้** — ยอมรับได้ แต่อย่าปล่อยเกินสองเดือน เพราะเนื้อหาคือสิ่งเดียวที่คนอื่นลอกไม่ได้
3. **อย่าเปิดการ์ดวิชาอื่นจนกว่าจะมีเนื้อหาจริง** — ป้าย "เร็ว ๆ นี้" ที่ค้างนานหลายเดือนทำร้ายความน่าเชื่อถือ
4. **หาคนใช้จริงระหว่างทาง** — ทันทีที่ด่าน A เสร็จ ให้เพื่อนในห้อง 10 คนลองใช้ แล้วค่อยตัดสินใจว่าด่าน D ควรเป็นแบบไหน
